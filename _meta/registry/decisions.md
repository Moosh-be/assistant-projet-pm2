# _projet/registry/decisions.md — décisions structurantes

> 1 ligne : `date | décision | source`. Seules les décisions qui changent la structure / le protocole sont consignées ici.

| Date | Décision | Source |
|---|---|---|
| 2026-11-01 | La couche du kit dans chaque projet = **`_projet/` (par défaut)** : fiche, backlog (1 fichier = 1 WP), registry, logs, report. Le manifeste reste `projet.md` à la racine du projet. | session du 01/11 (demande utilisateur « le répertoire, par défaut _project je pense ») |
| 2026-11-02 | **Verrouillé** : le nom de la couche n'est plus durci — c'est la clé **`meta_folder`** de la config machine `assistant.config` (racine du kit, gitignorée, wizard-générée). Valeur par défaut = `_projet`. « _project doit être une valeur par défaut mais venir d'une valeur de config » (verbatim). | session du 02/11 (WP-0017) |
| 2026-11-02 | **Changement de valeur par défaut : `meta_folder` = `_meta`** (était `_projet`). Termes pesés : `projet` (redondant « Mon-Projet/_projet »), `assistant` (liée à l'outil interchangeable + créée par le script natif sans IA), `artefact` (collision avec les artefacts de phase 01..05), `doc` (générique), **`meta`** (data *sur* le projet ; concept déjà nommé « couche méta » dans AGENT-projet §6 ; neutre FR/EN). Les dossiers créés avant le changement conservent leur nom (pas de migration rétroactive). | session du 02/11 (WP-0018) |
| 2026-11-03 | **Un projet assisté est autonome** : `assistant.ps1`/`.sh` sont copiés dans chaque projet par `new`/`add` (résout l'« ouvert » WP-0017 « /scan depuis un projet ») — `/statut` fonctionne donc depuis le projet (`statut` sans argument = projet du dossier courant). La **config machine** (racines) reste dans le kit : elle est machine, pas projet. | session du 03/11 (demande : « une fois opencode lancé, quelle commande tester ? ») |
| 2026-11-03 | **`update` : un projet met à jour son kit DEPUIS le projet** (sans revenir au repo du kit). Origine = ligne `kit_source: <chemin>` écrite automatiquement par `new`/`add` dans `_meta/registry/connexions.md`. Resync **zéro écrasement** : seuls les fichiers du kit manquants sont ajoutés (racine générique jamais `.gitignore` + `0*`/checklists/docs/tools + `.opencode/agent|command`, recursif) ; le contenu existant côté projet est sacré. Limite v1 : ajout de fichiers, pas de mise à jour de contenu (pas de diff/merge). | session du 03/11 (demande : « je devrais pouvoir lancer cet update sans retourner dans le repo qui gère les projets » — WP-0020) |
| 2026-11-02 | **Un projet n'est PAS forcément un projet de code** — c'est même la norme d'avoir un repo qui ne contient que `_meta/`. Conséquences : `statut`/`commence` acceptent un dossier sans `projet.md` (frontmatter de `_meta/fiche.md` = source de vérité, même que `projet.md`) ; `scan` classe un dossier sans kit mais avec `_meta/` en « à compléter » (projet sans code) ; `assistant new <nom> -doc` crée un projet minimal (seul `_meta/`, sans kit) — le kit s'ajoute ensuite avec `add` (zéro écrasement, `_meta` conservé). | session du 02/11 (WP-0019) |
| 2026-11-01 | Fin du concept « vault monolithe » : le kit s'appuie sur **des racines de projets (1..N)**, jamais de réorganisation des dossiers existants. | session du 01/11 (retour installation) |
| 2026-11-04 | **`remark` : journal des remarques au vol** — `assistant remark <texte>` (depuis le projet) note dans `_meta/registry/remarques.md` (1ʳᵉ entrée = header auto, puis 1 ligne datée). Les entrées marquées `[pour l'assistant]` : l'agent propose de les remonter au projet assistant (remontée = décision humaine, jamais auto). | session du 04/11 (demande : « il faut ajouter un journal des remarques au vol pour remonter dans le projet assistant les améliorations à y faire » — WP-0021) |
| 2026-11-04 | **Pédagogie PM2** — (1) `new`/`add` expliquent les 4 phases (Lancement → Planification → Exécution → Clôture, 1 gate = 1 checklist) + on attaque par la Lancement + une phase sautée sera signalée par le statut (« à faire par maîtrise ou curiosité ») ; (2) `statut` signale les **phases sautées** (gate non vert avant la phase courante) — source de vérité = la table d'avancement (section 3), gate vert = ☑/✅, `—` = pas de gate, rang par préfixe ASCII (Lan/Pla/Ex/Cl). | session du 04/11 (demande : « il faut être plus pédagogique au début, l'utilisateur ne connait pas l'assistant et connait mal PM² » — WP-0022) |
| 2026-11-04 | **Préfixe `/ap-` sur les slash-commands opencode** — l'espace slash est partagé avec les commandes du projet → le nôtre est réservé au préfixe `ap-` (assistant-projet), schéma `/ap-<nom>-<domaine>` : `/statut` → `/ap-statut-projet`, `/scan` → `/ap-scan-projets`. Les **commandes natives** du script (`assistant new/scan/statut/add/update/remark/commence`) **gardent leur nom** : pas d'espace de nommage partagé, pas de collision. Les phrases à l'agent (« commence le projet X ») = langage naturel, pas des commandes. | session du 04/11 (demande : « le /statut devrait être /ap-statut-projet, toutes les commandes devraient commencer par /ap- » — WP-0023) |
| 2026-11-01 | `AGENT-projet.md` (jamais `AGENTS.md`) : la note de routage IA doit rester **inerte** pour les outils, chargée explicitement par le protocole. | session du 26/10 (règle de nommage) |
